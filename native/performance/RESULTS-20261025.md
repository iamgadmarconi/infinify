# Native pan/zoom comparison — 25 October 2026

Keep the optimized scalar Dock path as the production default. Compile helpers
with `-O2`, skip redundant alpha setters only after a fresh alpha read, and cache
display metadata by reconfiguration generation while retaining fresh Space and
window checks. Transaction and plural-window batching remain explicit experiment
builds. The measurements do **not** establish a consistent smoothness winner.

The minimal WindowServer prototype loaded and passed its process identity and
exact-image ABI checks, then its sandbox refused the Unix listener's
`network-bind` with `EPERM`. It submitted **zero FRAME requests**. There is no
WindowServer latency result and no completed Dock-versus-WindowServer ranking.

## Retained measurement

The final comparison (`if-dock-comparison-10`) ran only in the authorized disposable
Apple Silicon `VirtualMac2,1` guest, macOS 27.0.1/26A434, with an independently
queried 60 Hz display. Each trial controlled the same eight opaque fixture
windows: two seconds of pan over 600 points and two seconds of zoom, 240 scheduled
poses. Five payload variants ran three times each, reversing order every round.
The client, fixture, observer, trace and machine configuration were pinned and
shared. Measurements were serial; no host builds or tests ran during this final
comparison.

[The complete 15-run data](results-20261025.json) preserves every trial's p99,
coverage, captured-pose gaps, artifact hashes, source clock, comparison decisions
and exact restoration. The raw recordings/replies/geometry and command logs are
retained in the worktree's ignored `target/native-perf/evidence/` directory.

Median of the three per-trial captured-pose p99 latencies:

- Frozen original, unoptimized build: **33.95 ms**; coverage **80.0–92.5%**.
- Frozen original, `-O2` only: **33.85 ms**; coverage **82.1–85.8%**.
- Current scalar, `-O2` and alpha dedup: **33.20 ms**; coverage **89.6–93.3%**.
- Transaction batch: **30.19 ms**; coverage **91.7–94.2%**.
- Plural-window batch: **31.44 ms**; coverage **85.8–93.8%**.

These medians are descriptive, including every trial. They are not proof that
transaction batching is fastest: trial ordering, scheduling tails, captured
coverage and refresh-phase alignment varied. Transaction versus scalar p99 was
33.75 versus 33.20 ms in round 1, 30.19 versus 41.21 ms in round 2, and 27.27
versus 24.50 ms in round 3. All three complete comparisons correctly returned
`winner: null`. The 90% coverage requirement was retained; low-coverage trials
were not discarded to manufacture a ranking.

The final observer's exact pixel scan took **0.37 ms p50, 0.72 ms p95 and
2.32 ms p99** (nearest-rank percentiles). A NEON scan replaces the original full scalar scan without changing
colour thresholds, spatial sampling, bounds or counts. Already-stale callbacks
are rejected before scanning. Its 12,799-case scalar equivalence contract passed
in the VM. Earlier observer recordings remain separate evidence; they are not
combined with this comparison.

Schema 2 uses shared `mach_absolute_time_ns` in Python and native processes.
Earlier schema-1 cross-process visible timing was invalid because the guest's
Python 3.9 monotonic clock was process-relative; it is excluded. Earlier temporary
comparison directories lost during guest reboot are not claimed as retained
evidence. The final data and raw recordings were copied to the host worktree
before the restoration reboot.

## What this measures

The independent ScreenCaptureKit display observer filters the exact fixture
windows and requires a fresh front-to-back native visibility witness. Captured
pose latency and unobserved pose intervals describe captured display composition.
Gaps may include capture omissions, repeated captures, sender supersession and
decoder omissions. They are **not** physical missed-refresh counts.

Acknowledgement round trips remain separate control-path measurements. There is
no physical pointer input-to-photon measurement, camera proof, third-party app
compatibility claim or general desktop UX acceptance in this result.

## WindowServer result

The pure-C prototype calls reviewed server routines on WindowServer's default
session/main execution context. Its image UUID and nine routine hashes are pinned
to the guest; see [SERVER-ABI.md](../windowserver-prototype/SERVER-ABI.md).
It retains raw placement matrices/flags and a fixed fixture scope and 60-second
maximum. The root loader bridges its birth/hash/parent checks to a strict kernel
unique-ID/executable-UUID/PID-version guard readable from the server UID.

The recorded startup sequence in `if-native-comparison-09` is constructor,
sidecar read, identity verified, ABI verified, worker started, then socket bind
denied. The kernel names the exact temporary Unix socket in its denial. Successful
loading and hash checks do not establish transform application or smooth output.

The temporary VM Library Validation preference was backed up before changing it;
its original state was absence of that preference file. The file was removed and
the guest rebooted to restore effective policy. Only the experiment's recorded
GPU payload directories are removed after that server instance exits. SIP and
boot arguments were not changed. The final restoration receipt is retained with
the evidence.
